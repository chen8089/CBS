1. Executive Decision
All eight pre-Phase 2 design decisions have been incorporated into the revised exact manifest. The prior design holds for Client User core data, Data Subject validation scope, consent-request uniqueness, repeat invitations, completed-request immutability, Flow-fault evidence, non-destructive remediation, Business Development sequencing and Experience Cloud sequencing are resolved.
The static metadata conclusion remains unchanged: the active Contact-created Flow currently creates a Consent_Request_Item__c for every new Contact with an Email, including Client_User Contacts. This is a P1 purpose-contamination defect and must be corrected before Category A is treated as implemented.
No metadata or Salesforce records were modified. The revised manifest is technically complete for final approval. Rows marked READY may be implemented only after final Phase 2 approval. Rows marked runtime-gated may be built in an isolated branch but must not be activated or deployed until the specified read-only Sandbox evidence and owner-approved remediation register are available.
A connected Salesforce Sandbox is not available in this execution environment. The authorised read-only runtime queries therefore remain an explicit external evidence gate rather than a completed analysis result.

5. Runtime Evidence Gate
The following read-only queries and setup checks are authorised. Cursor must export results without modifying data. Each result must include query time, org identifier, row count and the executing user. Personally identifiable values must be masked in review copies; full values may be retained only in the controlled remediation working file.
R01 - Contact counts by record type
SELECT RecordType.DeveloperName, COUNT(Id) total FROM Contact GROUP BY RecordType.DeveloperName
R02 - Client User records containing prohibited data
SELECT Id, AccountId, Email, Birthdate, Date_of_Birth__c, DOB__c, NRIC_FIN_Number__c, Passport_Number__c, ID_Type__c, ID_Number__c, MyInfo_Retrieval_Status__c, Consent_Type__c, Employment_Status__c, Report_Request_Status__c, Departure_Reason__c FROM Contact WHERE RecordType.DeveloperName = 'Client_User' AND (Birthdate != NULL OR Date_of_Birth__c != NULL OR DOB__c != NULL OR NRIC_FIN_Number__c != NULL OR Passport_Number__c != NULL OR ID_Type__c != NULL OR ID_Number__c != NULL OR MyInfo_Retrieval_Status__c != NULL OR Consent_Type__c != NULL OR Employment_Status__c != NULL OR Report_Request_Status__c != NULL OR Departure_Reason__c != NULL)
R03 - Legacy Client Admin role usage
SELECT Id, AccountId, Email, Portal_Role__c, Is_Active_Client_User__c FROM Contact WHERE RecordType.DeveloperName = 'Client_User' AND Portal_Role__c = 'Client Admin'
R04 - Data Subject-family access fields
SELECT Id, RecordType.DeveloperName, AccountId, Email, Portal_Role__c, Can_Approve__c, Is_Active_Client_User__c FROM Contact WHERE RecordType.DeveloperName IN ('Data_Subject','Singpass','Non_Singpass') AND (Portal_Role__c != NULL OR Can_Approve__c = TRUE OR Is_Active_Client_User__c = TRUE)
R05 - Duplicate Client Users by Account and Email
SELECT AccountId, Email, COUNT(Id) duplicateCount FROM Contact WHERE RecordType.DeveloperName = 'Client_User' AND Email != NULL GROUP BY AccountId, Email HAVING COUNT(Id) > 1
R06 - Active consent-request duplicates and status distribution
SELECT Data_Subject__c, Data_Subject__r.AccountId, Data_Subject__r.Consent_Type__c, Current_Status__c, COUNT(Id) itemCount FROM Consent_Request_Item__c WHERE Current_Status__c IN ('Pending','Sent','Viewed') GROUP BY Data_Subject__c, Data_Subject__r.AccountId, Data_Subject__r.Consent_Type__c, Current_Status__c HAVING COUNT(Id) > 1
R07 - Linked Experience Cloud users
SELECT Id, ContactId, Username, IsActive, Profile.Name, UserType FROM User WHERE ContactId != NULL
R08 - Effective legacy permission assignments
SELECT AssigneeId, Assignee.Username, PermissionSet.Name FROM PermissionSetAssignment WHERE PermissionSet.Name IN ('Set_Custom_Object_To_Partner','partner_community_User_Permissions_set')
R09 - Setup capacity and ownership checks
Manual read-only checks: Contact field-history tracked-field capacity; Shield retention policy; CBS Processing Queue active membership; deployment user Case create permission; relevant licence availability.

6.1 Mandatory stop conditions
The connected Sandbox baseline differs materially from the approved ZIP and the difference is not reconciled.
A Client_User record contains mixed-purpose Data Subject evidence and no data owner has approved its disposition.
Active consent-request duplicates exist and no retained active record has been approved.
CBS Processing Queue has no active member or the deployment context cannot create the fault Case.
Any Category B-I regression fails, including batch upload, consent status progression, report processing or Singpass staging.
Experience Cloud regression reveals broader access than the approved current-state baseline.
Cursor proposes a new object, API-name rename, automatic merge/delete or scope change not listed in the manifest.
