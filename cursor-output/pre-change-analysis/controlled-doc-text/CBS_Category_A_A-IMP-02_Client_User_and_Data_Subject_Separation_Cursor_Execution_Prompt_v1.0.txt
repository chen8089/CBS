2. Purpose, Scope and Traceability
This document is the controlled Cursor prompt for the first Category A implementation workstream. Its purpose is to separate Client User Contacts from Data Subject Contacts without creating a new custom object, without destroying valid data-subject evidence and without regressing Categories B-F.

Contact purpose and record-type controls for Client_User, Data_Subject, Singpass and Non_Singpass.

4. Non-Negotiable Target Design
Control
Required target
Purpose model
Contact remains standard. Client_User is the client-access identity; Data_Subject/Singpass/Non_Singpass are data-subject purposes.
Same-person rule
Use separate Contacts when one natural person has both purposes. Do not convert between Client_User and data-subject purposes.
Client User minimum data
FirstName, LastName, AccountId, business Email, Department, Portal_Role__c; Title and business Phone are optional.
Prohibited Client User data
DOB/Birthdate, ID/NRIC/FIN/passport, MyInfo, Employment Status, consent, report, departure and matching fields.
Data-subject access fields
Portal_Role__c, Can_Approve__c and Is_Active_Client_User__c are prohibited on the data-subject family.
Portal roles
Client HR User and Client Approver only. Client Admin is unavailable for new records unless separately approved.
Can Approve
System-derived from Portal_Role__c; users must not create contradictory combinations.
Active Client User
System-maintained from approved access/User state. Business Development cannot activate access by editing Contact.
Standard-first
No new custom business object. Use fields, record types, validation, Flow, layouts/pages, duplicate management, history and least privilege.
Cross-category safety
Preserve qualifying Category B processing and Categories B-F routes; no broad permission reduction without dependency evidence.
