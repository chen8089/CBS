7. 员工逐步执行流程
步骤 1　接收并核验文件包
目标：确认只使用本次交付的唯一受控文件包。
执行动作：
解压 CBS_A-IMP-03_Cursor_员工执行文件包_CN_v1.1.zip。
先阅读“00_请先阅读”中的本指南、README 和 Cursor 启动指令。
使用 SHA256SUMS.txt 核对所有附件。
任何文件缺失、同名异版或校验码不匹配时立即停止。
必须产出：
文件完整性核验记录、执行人员、日期和结果
停止条件：
校验码不匹配；文件来源不明；发现旧版混入
步骤 2　建立隔离工作区与 Git 分支
目标：确保 Phase 1 输出不污染受控 metadata。
执行动作：
将 metadata ZIP 解压到全新目录，确认 sfdx-project.json 与 force-app/main/default 存在。
确认 Git 工作区干净；必要时创建只读基线提交。
创建分支 feature/A-IMP-03-account-onboarding。
建立 controlled-documents 与 cursor-output 目录并复制受控文件。
必须产出：
分支名称、基线 commit、文件清单
停止条件：
工作区存在无法解释的修改；项目结构缺失
步骤 3　确认 A-IMP-02 前置依赖状态
目标：防止 A-IMP-03 在旧分支上设计或构建。
执行动作：
记录 A-IMP-02 当前状态：仅 Manifest 已批准、正在构建、已合并或已完成 as-built。
Phase 1 可以在 20260715 基线上分析，但必须标记所有与 A-IMP-02 重叠组件。
Phase 2 开始前必须取得最新 post-A-IMP-02 metadata，并重新执行 diff 与 Manifest 校验。
必须产出：
A-IMP-02 状态记录、重叠组件清单、未来 rebase 要求
停止条件：
无法确认 A-IMP-02 分支/版本；拟直接在旧基线上实施
步骤 4　在 Cursor 中加载受控执行规则
目标：明确本轮仅做分析，不实施。
执行动作：
用 Cursor 打开 Salesforce 项目根目录。
把“Cursor_启动指令_可直接复制.md”完整粘贴到 Cursor。
要求 Cursor 先列出识别到的 7 个受控文件、版本、优先级、基线 hash、分支与 Phase 1 边界。
明确最终停止语句为 AWAITING A-IMP-03 MANIFEST APPROVAL。
必须产出：
Cursor 启动确认、文件识别结果、权限边界声明
停止条件：
Cursor 读取旧版；提议直接修改/部署；未确认 A-IMP-02 依赖
步骤 5　执行 metadata 全量扫描
目标：验证当前组件、API 名称、引用与冲突。
执行动作：
扫描 Account、Task、Opportunity、Contract、Files、Flow、Approval、Apex、Layout、FlexiPage、StandardValueSet、Permission、Application。
搜索 Client_Code__c、Client_Status__c、Notification_Email__c、SLA_Days__c、Approval_Required__c、Task Type/Status 及所有状态常量。
逐项验证 A-IMP-03 Manifest 模板，标记 FOUND、NOT FOUND、NAME MISMATCH、DEPENDENCY。
规范 API 名称冲突时停止，不得创建替代名称。
必须产出：
当前状态清单、依赖图、API 校验版 Manifest、候选文件变更清单
停止条件：
发现未记录自动化；名称冲突；需要新对象/Apex/LWC
步骤 6　执行 R01–R12 只读证据收集
目标：补足 metadata 无法证明的记录、文件、权限、功能和容量证据。
执行动作：
由 Sandbox 操作人员执行只读 SOQL/Setup 检查；Cursor 只生成脚本和分析结果。
每项记录 Org ID、用户、时间、查询文本、行数和输出路径。
评审副本必须遮蔽客户名称、用户名、联系人和合同信息。
输出存入 cursor-output/runtime-evidence。
必须产出：
R01–R12 结果、Setup 截图/导出、运行时证据登记表
停止条件：
任何 DML；无法确认 Org/用户；基线与 Org 漂移未解释
步骤 7　建立现有 Account 基线决策登记表
目标：确保现有 Active/Inactive 客户不会被自动视为已完成入驻。
执行动作：
逐条记录 Account 当前状态、Client Code、Closed Won、Contract、File、Task 和活动外部 User 证据。
为每个 Account 提出：重建证据并批准、授权 grandfather exception、启动新入驻周期、暂停待补证或排除为非 CBS 客户。
Client Code 重复或缺失只形成建议，不自动修改。
提交 CBS 业务/数据负责人审批。
必须产出：
现有 Account 基线决策表、Client Code 整改清单、未决例外
停止条件：
未取得业务负责人决定；拟批量自动设为 Approved/Active
步骤 8　完成影响报告与精确 Manifest
目标：将静态分析和运行时证据转化为可审批实施范围。
执行动作：
完成 01_pre_change_impact_report.md。
完成 02_exact_metadata_manifest.csv，并为每行记录 READY、RUNTIME GATED、DEFERRED、HOLD 或 ANALYSIS ONLY。
明确 metadata 部署与运行时激活/数据处理是不同门槛。
生成 T01–T24 测试计划、部署草案和回滚草案。
所有 Manifest 外组件只能作为“待批准新增项”，不得实施。
必须产出：
影响报告、精确 Manifest、测试计划、部署/回滚草案、冲突决策表
停止条件：
存在未决 P1/P2；无法保证幂等性；需要跨工作流修改
步骤 9　提交审批并停止
目标：将完整 Phase 1 证据包交项目负责人审批。
执行动作：
把全部输出放入 cursor-output 对应目录。
记录 branch、baseline commit 和 latest commit；Phase 1 不应包含 metadata 源文件改动。
Cursor 最后一行必须精确写：AWAITING A-IMP-03 MANIFEST APPROVAL。
收到书面 Manifest 批准前，不得开始 Phase 2。
必须产出：
完整审批包、Git 记录、最终停止语句
停止条件：
无书面批准；证据不完整；源文件已被修改
