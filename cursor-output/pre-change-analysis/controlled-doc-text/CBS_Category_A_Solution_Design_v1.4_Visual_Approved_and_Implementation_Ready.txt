1. Governance and Purpose
The latest Salesforce metadata is the authoritative technical source for understanding the current CBS implementation. It establishes what is retrieved in the sandbox snapshot; it does not by itself prove that every current behaviour is required or suitable for the target state.
The CBS Salesforce solution shall be developed and maintained using a category-led, design-controlled lifecycle. Each business-process category must progress through requirements confirmation, solution design, visual approval, implementation, as-built verification and user acceptance testing in that order. The approved Solution Design is the authoritative target-state source for implementation prompts, Salesforce configuration, visual prototypes and UAT scenarios.

11. A-WS-01 - Client User and Data Subject Separation
Design statusApproved target design. Section 11 was approved on 18 July 2026. It remains subject to as-built verification after implementation and does not itself authorise implementation before the remaining Category A design gates are completed.
11.1 Objective, scope and controlling requirements
The purpose of A-WS-01 is to establish a clean Contact-purpose boundary so that a client organisation user cannot enter the data-subject consent lifecycle, and a data subject cannot acquire client-access administration attributes or portal privileges. The design uses the standard Contact object with record types, layouts, Lightning pages, validation rules, permission sets and Flow entry criteria.
Control
A-WS-01 position
Requirements in scope
A-REQ-005, A-REQ-007 to A-REQ-010, A-REQ-018, A-REQ-023 and A-REQ-024.
Locked decisions applied
A-DD-001 standard-first architecture; A-DD-003 Case-based access governance; A-DD-004 no additional identifiers; A-DD-010 Business Development and administrator authority.
In scope
Contact record-type purpose, fields, page layouts, Lightning pages, actions, Flow guards, FLS, duplicate prevention, audit and data remediation.
Out of scope
Detailed data-subject consent requirements, client access Case approval implementation, User provisioning, quarterly review and final Experience Cloud screens.
Custom object position
None required. Contact, User, Case, Account, Flow, validation rules and permission sets are sufficient for this workstream.

11.3 Target Contact purpose model
Contact remains the standard person record. Record type identifies the business purpose of the record, but permission sets, fields, automation and page experiences enforce the separation. A record must not be reused across the two purposes.

Figure 1 - A-WS-01 target Contact purpose separation
Same-person ruleWhere the same natural person is both a bank client user and a data subject, CBS shall maintain separate Contact records for the two purposes. The client-user Contact supports the User and access lifecycle; the data-subject Contact supports consent, report and departure lifecycles. The records must not be converted between purposes.

12.7 Maker-checker approval process
Approval element
Target design
Submission eligibility
Record type, Account, Client_User Contact, request type, reason, target role and named approver pass all validation. The Account onboarding gate is approved before New Access or Reactivation.
Initial submission actions
Populate Submitted_By__c, snapshot existing access, set Status to Pending Approval, set Approval Status to Pending and lock approval-relevant fields.
Approver assignment
Assign the approval step to Assigned_Approver__c. The selected user must be active and authorised for CBS client-access approval.
Separation of duties
Assigned Approver cannot equal Submitted By. Business Development does not receive approval authority. A production user must not hold both maker and access-approver capabilities without a documented exception.
Approval
Set Approval Status to Approved and Case Status to Approved. Notify the authorised administrator and maker.
Return
Require checker comments, set Approval Status to Returned and Case Status to Returned, unlock the request and notify the maker. The amended request must be resubmitted.
Rejection
Use only where the request must not proceed. Set Approval Status to Rejected and close the Case with a required reason.
Recall
Allow the submitter to recall a pending request before decision; return it to Draft and retain Approval History.
Post-approval control
Approved access scope is immutable. Any later material change requires a new linked Client Access Request Case.
12.8 Provisioning, change, suspension and revocation
Request type / stage
Administrator procedure and evidence
New Access
Administrator confirms approved Case, uses the admin-only Contact/User administration experience to create or enable the external User, assigns the approved profile and role package, records Related User and implementation evidence, then sets Contact access summary fields.
Change Role / Permissions
Administrator removes obsolete approved access, assigns the requested approved package, updates Contact Portal Role and Can Approve through controlled automation, records the before/after state and completes the Case.
Suspend Access
Administrator prevents login using the approved Salesforce user-suspension control, records the reason and timestamp, sets Is Active Client User false and retains the User and Case history.
Reactivate Access
Administrator confirms the approved role and restores the User only after approval, then reassigns the approved access package and updates the Contact summary.
Revoke Access
Administrator removes access and deactivates the User after required Salesforce ownership and dependency checks. Historical Contact, User, Case and approval evidence is retained.
Implementation failure
Set Case Status to On Hold, capture non-sensitive implementation notes and next action, and do not mark the Contact active.
Completion
Record Related User, Implemented By and Completed At. Close only after the User state and permission assignment match the approved request and the required notification is issued.

A-WS-03 defines the initial client-onboarding control model from commercial completion through CBS readiness approval. Account is the authoritative onboarding record. Standard Tasks provide the detailed checklist. Opportunity, Contract, Salesforce Files and Client User Contacts provide supporting evidence. Business Development coordinates and submits the onboarding; an authorised administrator performs the final independent assessment. Approval updates the authoritative Account gate; access governance consumes that gate but does not duplicate the onboarding evidence.

All mandatory Tasks for the current cycle are Completed with required evidence. Task count fields agree with the actual related Tasks.
Account validation
Client Code, owner, Notification Email and approved simple client settings are complete; Client Status is Onboarding.
Opportunity validation
At least one related Opportunity is Closed Won.
Contract validation
At least one Contract is related to the Account, contains Start Date and Contract Term, has a system-calculated End Date, and is ready for or already in Activated status.
File validation
The mandatory contract-upload Task is complete and the submitter confirms that the executed document is visible in Contract Files. The checker independently verifies the File.
Submission actions
Populate Submitted By and Date, set Onboarding Status Pending Approval, submit the Account to the named authorised administrator approval queue or approver, and lock approval-controlled fields.
Separation
The submitter cannot approve the same onboarding. Business Development receives no onboarding-approval permission.
Approval
Administrator verifies evidence, activates the Contract where required and permitted, approves the Account, sets Onboarding Approved true, Approved By/Date, Completed Date, Onboarding Status Completed and Client Status Active.
Return
Checker comments are mandatory. Set Onboarding Status Returned, keep Onboarding Approved false, copy a concise return instruction to the Account, unlock the record and notify Business Development.
Cancellation
An authorised administrator may cancel before completion using a controlled action and mandatory reason. The access gate remains false.

Design statusApproved target design. Section 14 was approved on 18 July 2026. It remains subject to as-built verification after implementation and does not authorise implementation before the remaining Category A design gates are completed.
14.1 Objective, scope and controlling requirements
A-WS-04 establishes the security boundary between CBS internal users, an authenticated external client user, other users in the same client organisation, users belonging to different client organisations and unauthenticated guests. It applies the access and onboarding gates approved in Sections 12 and 13. It does not define the detailed operational permissions for consent, departures, report fulfilment or support; those permissions remain owned by their process categories and must conform to this isolation model.
Control
A-WS-04 position
Requirements in scope
A-REQ-005 to A-REQ-010, A-REQ-013, A-REQ-015 to A-REQ-018 and A-REQ-022 to A-REQ-024.
Locked decisions applied
A-DD-001 standard-first; A-DD-003 Case-based access; A-DD-004 data minimisation; A-DD-005 maker-checker; A-DD-007 onboarding gate; A-DD-008 quarterly review; A-DD-010 Business Development and administrator authority.
Identity anchor
Every external User is linked to one Client_User Contact, and that Contact is linked to one authorised Account.
Primary control objective
A client user can perform only approved role functions for the authorised Account and cannot discover, query, open, export or receive data belonging to another Account.
Category A external boundary

Standard-first position

14.3 Target external-access model
The target model treats the external user identity, authorised Account, functional role and controlled page as separate but cumulative controls. No single control is sufficient. Record sharing limits the records that can be reached; profiles and permission sets limit objects, fields, classes and actions; Experience Cloud pages limit the user journey; Apex and LWC revalidate the Account boundary for every server request.

14.7 Sharing design for operational records
Operational custom objects are designed in their owning process categories, but any record exposed to Experience Cloud must satisfy the following common Account-isolation contract. This section does not approve their business actions or field sets.
Control
Mandatory standard
Direct Account relationship
Every independently shared external record has a required and system-controlled Client_Account__c lookup, or is master-detail to a parent that already provides secure Account access.
Creation
The Account value is derived from the running external User context. A client-supplied Account ID is ignored or rejected.
Mutation
External users cannot change Client Account after creation. Internal correction requires an audited administrative process.
Sharing set
Where standard sharing sets are suitable, map User.Account to the record Client Account lookup at the minimum required access level.
Secure parent
Child records inherit access only where the relationship and sharing model technically enforce the parent boundary. A simple lookup is not treated as inherited security.
Controller scope
Every Apex query and mutation includes the resolved authorised Account, even when with sharing is used. Sharing and explicit Account scope are defence in depth.
Direct record ID
A request containing a record ID re-queries the record with Account scope before returning data or performing an action.
No recognised Account field
The controller returns no rows and no action. It must not silently continue without an Account filter.
Same-client collaboration
Read or edit among users of the same Account is granted only where the process requires it and the approved role package permits it.

16. A-WS-06 - Contract Lifecycle and Files
Design statusControlled detailed design for approval. It defines the standard Contract record, dates, status, Salesforce Files, internal access, activation, Opportunity and onboarding handoff, and the manual renewal, amendment and termination conventions.
16.1 Objective, scope and controlling requirements
A-WS-06 establishes the simplest controlled Contract model for Category A. CBS uses the standard Contract object, standard Contract fields and Salesforce Files. Business Development creates and maintains the Contract; authorised administrators retain correction and override authority. External users have no Contract or Contract File access. The design does not introduce a custom Contract object, a custom End Date or a contract-management application.

16.3 Target Contract lifecycle
The target lifecycle is deliberately small. A Closed Won Opportunity triggers a Contract follow-up Task, not automatic Contract creation. Business Development creates the standard Contract against the Account, enters the standard dates, uploads the signed or effective agreement, performs the controlled activation action and completes the follow-up Task. Contract activation does not itself activate the Account or create external users.

17.4 Default SLA resolution and boundary
Category A owns the client-level default only. The report-request and other operational categories own due-date calculation, business hours, pausing, escalation and exception behaviour. Until those categories approve a different calculation, the current whole-calendar-day model is retained, but the value must be resolved on the server and never trusted from the client request.
SLA control
Target rule
Authoritative source
Use Account.SLA_Days__c when it contains a valid positive whole number. Otherwise use the controlled system default of five.
Client input
Ignore or remove any SLA value supplied by LWC, Experience Cloud, browser, API request or external user. The server resolves the value from the authorised Account.
Operational snapshot
At creation, stamp the resolved value on Case.SLA_Days__c and calculate the Case due and warning dates. Later Account changes do not alter an existing Case unless an approved operational process explicitly recalculates it.
Account matching
Resolve the default only from the Account authorised for the signed-in User and requested-by Contact. Cross-Account lookup or override is prohibited.
Edit authority
Administrator maintains the default. Business Development may view it and may request a change through the controlled internal process; external users have no edit authority.
Validation
Allow a positive whole number only. The implementation must define a conservative maximum during the operational-category design and reject zero, negative, fractional or unreasonably large values.
Future change
Business-hours calculations or product-specific SLAs require an explicit later design amendment. They are not inferred from current fields.

18. A-WS-08 - Screen Specifications and Category A Design Closure
18.1 Objective, scope and controlling requirements
A-WS-08 converts the approved Category A process, data, security and control design into controlled screen-definition records. It does not create implementation prompts or UAT cases. It establishes exactly what must be visualised, which standard Salesforce surface owns each screen, which roles may use it, what information and actions are permitted, and what must never be shown.
Control

Requirements in scope
A-REQ-001 to A-REQ-025 and all approved design controls in Sections 11 to 17.
